- ~~No per-NPC personality / all crowd NPCs behaved identically~~ — added a trait system: one Primary (`WalkIn`/`Hasty`/`Loiterer`, mutually exclusive, governs overall movement) plus any number of independent Modifiers (`Weary`/`Caffeinated`/`Thief`, stack freely) per Crowd NPC. Walk-In seeks a ticket line near spawn; Hasty skips every detour; Loiterer wanders forever and never boards; Weary rests more; Caffeinated detours to a Cafe zone then gets a permanent speed/alert-sensitivity boost; Thief autonomously steals another Crowd NPC's held item. Also added: a generalized Line Impatience meter (all queued Crowd NPCs, not just Walk-In — gives up to a seat or leaves the airport once met), dynamic Line-slot positioning (walk behind whoever's actually ahead, not a fixed grid), Basic-node position spread (NPCs no longer converge on one exact point), and Auto-search backtrack prevention (won't route into a node whose Link immediately sends the NPC back the way it came). Two new node types — Interaction Node (cosmetic dwell, Vending Machine/Inquiry Desk/Shelf/ATM) and Stand Node (standing equivalent of Seat) — plus `Location`/`Occupied` node attributes. The Conveyor checkpoint now does **real automated contraband detection** (`ForcePanic` on a hit, no TSA player needed), not just cosmetic. NPC spawn point moved to `<ActiveMap>.Spawns.NPC`, matching `SpawnService`'s existing convention.
- ~~AI decisions ran centrally on the main thread, not "autonomous"~~ — every Crowd NPC now gets its own **Actor** (`NPCBrainScript.server.luau`, `ServerScriptService/NPCBrain/`) running genuinely parallel Luau. The Actor computes only the *category* of decision (Loiter/Theft/CafeDivert/Rest/Wander/Proceed) from a plain-data snapshot — pure `math.random()`, no Instance access — and reports back via a shared `BindableEvent`; `NPCAIService` on the main thread resolves the specific target and performs all mutation. Decoys don't get a brain Actor (kept on their existing scripted divert behavior). See NPC-AI.md's "Brain Actors" section for the full protocol. **Not done**: Decoys getting the same treatment — out of scope, intentionally scripted/deterministic-feeling.
- ~~Two `ItemService.Shared.X` calls (`SpawnItem`) crashed on the first live playtest~~ — `NPCAIService`/`ItemSpawnService` (and a pre-existing `StealService` call) were calling `ItemService.Shared.ForceDropItem`/`SpawnItem`/`EquipNPCItem`, but `require(script.Parent.ItemService)` already returns the `Shared` table directly (`ItemService.luau` does `return Shared`) — so `.Shared` was indexing a field that doesn't exist. Fixed all 6 call sites across `NPCAIService.luau`, `ItemSpawnService.luau`, and `StealService.luau` to call directly on the required module.
- ~~`ItemService.SpawnItem`/`CloneItemTemplate` couldn't find item templates~~ — `ItemsConfig` keys (and every internal caller) use un-spaced PascalCase names (e.g. `"DuffleBag"`), but the actual Model templates under `ReplicatedStorage.Assets.Items` are authored with a space before each word (e.g. `"Duffle Bag"`). `Local.CloneItemTemplate` now tries the space-inserted form first (`itemName:gsub("(%l)(%u)", "%1 %2")`), falling back to the literal name.
- ~~NPCs walked straight through/into walls between nodes, movement felt rigid~~ — the node-to-node movement was a single straight-line `MoveTo` with one raycast to clip short of a direct obstruction; anything not directly in that one raycast's path (a corner, an offset node) was never routed around. Also added per-NPC `WALK_SPEED_JITTER` so the crowd doesn't move in lockstep. (2026-07-17: the Actor-per-NPC rewrite originally deferred here — see the trait-system entry above — was later built after all, once the trait system grew large enough that the user wanted the AI decisions genuinely parallelized.)

- ~~Airplane/boarding announcement cycle (Zone D gate)~~ — new round-scoped `GateService.luau` (`sync/ServerScriptService/Services/`) runs a repeating 4-stage cycle for the entire `InProgress` state, purely via `Workspace` attributes (`GateStage`/`GateTimeLeft`/`BoardingOpen`), same authoritative-attribute convention as `RoundService`'s `RoundState`/`TimeLeft` — no Network remotes. Stages: `Arrived` (plane taxis in, gate closed) → `Boarding` (`BoardingOpen=true`) → `Departing` (gate just closed) → `Waiting` (empty gate) → loops. Durations are `isStudio`-scaled like `RoundService`'s own constants (currently 15/45/15/15s = 90s/cycle live, 10/15/10/10s = 45s in Studio, tuned after the initial pass) — fast-loop pacing was the explicit choice over a slow 1-2-cycles-per-round design, so the boarding window recurs often. Four integration points, all done this pass: (1) **`DepositService`** — `StartDeposit`/`CompleteDeposit` now also require `Workspace.BoardingOpen == true`, and a new `BoardingOpen` attribute watcher cancels every in-flight deposit the instant the gate closes (previously deposits were always active whenever `InProgress`+team+contraband checks passed). (2) **`NpcService`** — the Depart Node stopped being a permanent dead end: `Local.OnArrive` stamps `record.departArrivedAt` on arrival there, and the Heartbeat loop now holds a waiting NPC (no decision requests, same shape as the existing Seat/Line-dwell gates) until `BoardingOpen` is true and `NPCConfig.BOARD_DWELL` (3s) has passed, then despawns it via `task.defer(Local.CleanupNPC, ...)` — the NPC "boards the plane," closing the Commuting loop that previously just stalled forever once a crowd NPC reached the gate. (3) **Client Hud** — new `GateController.luau` (mirrors `RoundController`'s attribute-read+signal pattern exactly) feeds a **new `Hud.Status` frame** (a single `Label` TextLabel, added directly in Studio this session — not code-created) via `Hud.luau`'s `Local.UpdateStatus`; text is stage-templated (`"Airplane has arrived — boarding in %ds"`, etc.) and the frame auto-hides when `GateStage` is unset (outside `InProgress`). In-world signage/PA sound props were **explicitly deferred** (no Gate asset exists in any map template yet) — `GateService`'s stage-setter is commented as the integration point (`Workspace.GateStage`/`GateTimeLeft`, same attributes the Hud reads) for whenever that asset gets built, no service-side wiring needed when it does. (4) **Departing Door animation** (added 2026-07-21, same file) — `GateService` resolves `<ActiveMap>.Assets["Departing Door"]`'s `AnimationController`/`Animator` fresh each round and drives it directly from `Local.SetStage`: entering `"Boarding"` plays the one-shot `openAction` track, entering `"Departing"` plays `closeAction`. Two looped Idle tracks (door held open/closed) hand off from the Action tracks via animation-event markers authored on the clips themselves (`"Open"` marker on `openAction`, `"Close"` marker on `closeAction`) rather than the tracks' `Stopped` event, since the Action clip keeps playing a short settle after the marker. Soft-fails (warns, `Open/CloseDoor` become no-ops) if the door/controller/animator isn't found — same tolerance as `Spawns.NPC`/`ItemSpawns`/`Nodes` elsewhere.
- ~~No item-spawn system in the map~~ — `ItemSpawnService.luau` reads an `ItemSpawns` folder (same per-round-clone convention as `NodesFolder`) from the active map; each spawn point is a `BasePart` with optional `Items` (comma-separated explicit item names) and `ItemsType` (comma-separated categories, default `"Non-functional"`) attributes that join into one weighted candidate table (`spawnWeight`, falling back to 10 if unset) and pick via `ItemService.Shared.SpawnItem`. Respawns 15s after the spot's item is picked up or destroyed (tracked via `Parent` changing off the spawned item). Added `itemType` (`"Chaos"` | `"Non-functional"`) to all 31 non-bag items' `properties`, plus `spawnWeight` to the 7 "chaos prop" items that didn't have one (`WetFloorSign`, `ToyGun`, `SmokeBurst`, `StinkBurst`, `AirHorn`, `FireExtinguisher`, `OverchargedBattery`). Deliberately excluded from spawning at all (no `spawnWeight`/`itemType` added): `ScannerWand`/`Handcuffs`/`Taser` (TSA default tools) and `FakeBoardingPass`/`DoubleEspresso`/`PaddedJacket` (paid loadout unlockables) — letting those spawn free on the floor would undercut the Token-unlock economy (Project.md section 7).

## Notes

- Currency is internally still `coins`/`AddCoins` (`stats.coins`, `Coins` leaderstat) — "Terminal Tokens" is only the in-fiction name. Don't rename the internal identifiers without good reason; it'd touch `DataService` leaderstats and UI.
- Server round state is authoritative via `Workspace` attributes (`RoundState`, `TimeLeft`, `QuotaTotal`) — any future client feature needing round state should read through `RoundController`, not touch `Workspace` directly.
- **NPC AI is `NpcService`** (`sync/ServerScriptService/Services/NpcService/`, rebuilt 2026-07-17 — see `mds/NPC-AI.md`). Every map template's `Nodes` folder is now **zone-subfoldered**: `Nodes/Lobby`, `Nodes/Concourse`, `Nodes/Platform`, `Nodes/Cafe`, `Nodes/Souvenir`, `Nodes/Convenience`, each containing ordinary node `BasePart`s (with a child `Attachment`, optional `Link` `ObjectValue`) and/or a `Line Node` folder (a group of individually-occupied physical queue-slot parts, `Link`-chained, tracked via `PeopleInLine`/`MaxCount` attributes). `Depart Node` is the one part parented **directly under `Nodes`**, not inside a zone subfolder. A Line Node group's main slot can carry an `Entry` `ObjectValue` pointing at a separate `Entry Node` part — NPCs detour there before joining the line. Only the `Linear` Behavior exists so far (no traits) — it walks the fixed backbone `Lobby → Concourse → Platform → Depart`, ignoring the Cafe/Souvenir/Convenience side-zones (those are valid per `NPCConfig.ZONE_ADJACENCY` but not part of Linear's own sequence). No `Nodes` folder/no nodes just means `NpcService` logs a warning and spawns nothing that round — it fails soft, not hard.
- Every map template also needs a `Spawns.NPC` `BasePart` (sibling to the existing team spawn zones under `Spawns`) — NPCs spawn at a random point inside it, matching `SpawnService`'s `Spawns.<TEAM_NAME>` convention. Missing it just means a warning and a fallback to a random node position.
- Every map template also needs an `ItemSpawns` folder for `ItemSpawnService` — plain `BasePart`s, optionally with `Items` (comma-separated item names) and/or `ItemsType` (comma-separated `"Chaos"`/`"Non-functional"`, defaults to `"Non-functional"`) string attributes. Same soft-fail behavior as `NodesFolder`: missing/empty just means a warning and no items that round.
